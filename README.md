# Fleet Monitor

**An observability platform with an agentic root-cause analyst and eval harness that keep every design decision measured, not asserted.**

## What this is

Fleet Monitor deliberately spreads its data across five stores, Postgres, Redis, ClickHouse, InfluxDB, Neo4j — one job per store, so each choice can be benchmarked against the alternative on the same real workload instead of just asserted. The five [comparison write-ups](docs/comparisons/) are results from reproducible failure conditions.

Three things this project is built to test, in priority order:

1. **Storage selection** — build the same feature on Postgres first, hit its limits under real load, move to a specialized store, measure the difference.
2. **Ingest engineering** — buffering, batching, and backpressure tested at real write volume, not toy volume.
3. **Agent engineering** — a tool-using agent with real guardrails, scored by a 20-scenario eval harness against known ground truth rather than demoed against a happy path.

Everything the agent queries during an investigation or an eval run is self-generated by real failing processes in the demo mesh. Synthetic data appears in exactly two places: backfilled chart history (`scripts/backfill.js`, so the Overview page isn't empty on a cold start) and load-test/comparison-benchmark bursts (`scripts/*.js` under [Comparison write-ups](#comparison-write-ups)).

## How it works

A purpose-built mesh of eight services (`mesh/`) generates real telemetry and fails on command via a chaos endpoint (`ok` / `slow` / `error` / `dead`). A probe library shipped into every service reports metrics, logs, dependency topology, and liveness to a central Fastify backend (`server/`), which routes each data shape to a fit-for-purpose store. A read-only AI agent (`server/agent/`) takes a symptom in plain English, walks the dependency graph, reads evidence through the same query layer the UI uses, and reports one or more root causes with a blast radius. Because every failure is deliberately induced, an eval harness (`evals/`) scores the agent against known ground truth and publishes its failure modes — see `docs/agents/domain.md` and `CONTEXT.md` for the vocabulary this is built on.

## Architecture

```
                                    ┌─────────────┐
   traffic-generator ────────────▶ │   nginx     │ ── access logs ──▶ nginx-log-tailer
                                    │ (TLS/proxy) │                          │
                                    └──────┬──────┘                         │
                                           │ /api                           │
                                           ▼                                │
   web ──▶ checkout ──▶ api-gateway ──┬──▶ auth-service ──▶ session-store   │
    (demo mesh, chaos-controlled) ────┼──▶ payments ──────▶ ledger-db       │
    each service: probe + chaos ctrl  └──▶ inventory ─────▶ ledger-db       │
                        │                                                   │
                        │ metrics / logs / topology / heartbeat             │
                        ▼                                                   │
              ┌────────────────────────────────────────┐                   │
              │  Fastify backend (server/)              │ ◀─────────────────┘
              │  ingest/  ─ metrics, logs, topology      │
              │  query/   ─ shared by UI and agent       │
              │  agent/   ─ investigation loop            │
              └──┬────────┬────────┬─────────────────────┘
                 │        │        │
                 │        │        └────────────────────────▶  ClickHouse    logs
                 │        └─────────────────────────────────▶  InfluxDB      metrics
                 │        (Redis buffers logs; TTL liveness)   Neo4j         topology
                 └───────────────────────────────────────────▶ Postgres      registry
                                                                              investigations
                                           ▲
                                           │ SSE trace + finding card
                                    ┌──────┴──────┐
                                    │  web (React) │  Overview · Map · Investigate
                                    └─────────────┘
```

| Store | Job | Why |
|---|---|---|
| **Postgres** | Service registry, investigation history | Relational core; FKs and transactions |
| **Redis** | Log write buffer, liveness TTLs | ClickHouse *fails* (`TOO_MANY_PARTS`) without batching — [write-up #2](docs/comparisons/02-batched-vs-per-row-clickhouse-inserts.md) |
| **ClickHouse** | Log storage and search | Columnar, high-cardinality substring search beats Postgres FTS on the query shape logs actually need — [write-up #5](docs/comparisons/05-tsvector-vs-clickhouse-log-search.md) |
| **InfluxDB 3** | Numeric time series | Retention + downsampling as config, not hand-built — [write-up #3](docs/comparisons/03-influxdb-vs-clickhouse-metrics.md) |
| **Neo4j** | Dependency graph, blast radius | Variable-depth traversal beats a recursive CTE at depth 4 — [write-up #1](docs/comparisons/01-neo4j-vs-recursive-cte.md) |

## Comparison write-ups

Five write-ups in `docs/comparisons/`, each *tried → limit → measured*, with real numbers from the actual stores — not estimates. These are what the polyglot design rests on:

| # | Comparison | Proves |
|---|---|---|
| [1](docs/comparisons/01-neo4j-vs-recursive-cte.md) | Neo4j vs. recursive CTE | Graph traversal choice was evaluated, not assumed |
| [2](docs/comparisons/02-batched-vs-per-row-clickhouse-inserts.md) | ClickHouse batched vs. per-row inserts | Redis log buffer is required, not decorative |
| [3](docs/comparisons/03-influxdb-vs-clickhouse-metrics.md) | InfluxDB vs. ClickHouse for metrics | Addresses the one contested store overlap head-on |
| [4](docs/comparisons/04-aggregated-vs-raw-tool-outputs.md) | Aggregated vs. raw agent tool outputs | Quantifies the context-engineering work |
| [5](docs/comparisons/05-tsvector-vs-clickhouse-log-search.md) | Postgres `tsvector` vs. ClickHouse log search | Log-store choice was evaluated, not assumed |

The expected hard question is *"You have ClickHouse — why a second time-series database?"* Write-up #3 is the answer: InfluxDB gives retention and downsampling as configuration; ClickHouse needs it hand-built. At this project's scale either store is fine — in production I'd consolidate on ClickHouse and drop InfluxDB. The write-up exists so that's a measured trade-off, not a shrug.

## Running it

```
cp .env.example .env   # fill in passwords; set ANTHROPIC_API_KEY to run the agent
docker compose up -d
```

Then open `https://localhost` for the UI (Overview / Map / Investigate pages), or induce a failure directly against a mesh service, e.g. `curl -X POST localhost:4004/chaos -d '{"mode":"dead"}'`.

Run the eval suite (20 chaos scenarios scored against known ground truth) with `node evals/run.js`, or `node evals/run.js --replay` for the ~1-minute capture/replay iteration loop once fixtures exist. See `docs/PRD.md` and `fleet-monitor-docs.md` for the full design.
